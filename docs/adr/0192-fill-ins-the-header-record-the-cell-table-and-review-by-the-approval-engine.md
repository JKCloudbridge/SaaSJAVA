# ADR-0192: Fill-ins: a header record and a cell table, pinned to the version of the template, reviewed by the approval engine

- **Status:** Accepted (the product owner delegated every decision on 2026-10-23 after the plan and its questions were shown; the recommendation of each question was built)
- **Date:** 2026-10-23
- **Sprint:** FF1 (Functional track, the following set, first half)

## Context

A template is published to the people of a department. A person opens it and fills it in: they type into the cells the template marks as input, add rows where it allows it, and send the fill-in to be checked. About 1,000 a day may be made from one template, each about 50 rows by a few columns (ADR-0173 section 6). Each is pinned to the version of the template it was started on and changes neither the template nor another fill-in. This is the first half of the set (FF2: attachments, reportable columns, reports, archiving). The questions were: where a fill-in lives (FA5 chose tables of the cluster; ADR-0191 asks that the question be decided again, deliberately), how it is reviewed, who sees which, and the shape of the stored cells without the real filled example (open item B of the business file is still postponed).

## Decision

### 1. A header record and a cell table (not tables of the cluster only)

- **The header is a record** of a shipped object, `InspectionFill` (private by default, kept for good, nothing an administrator changes). The record store gives it what a record has: an owner, a place in lists and search, shares, record-level security and, above all, **the approval engine**, which can pin a request only to a record (ADR-0174). Its three fields are written only by the platform (`name`, `templateId`, `status`; the loader allows only text and yes/no for such a field, so the template is the text of its identifier, which also means a member cannot re-point it).
- **The cells and the pin are a table of the sheets module**, `sheet_fill` (V069): the cells as one jsonb document (up to 1 MB, compressed by PostgreSQL), the sheet and version number the fill-in is pinned to, the status, a count of rows and the row version. A record of the generic store cannot hold the cells (flat values, 256 KB), and a list of fill-ins must never read them.
- **Why not tables only (as FA5):** the reason FA5 had (a detail record inherits no security from its master) does not apply, because a fill-in is not a detail of a template: it has its own owner and its own visibility. What decided it is the approval engine, which gives the lock, the tasks, the inbox, the history, the reminders and the notices for nothing; with tables only, review would have been an act built from nothing.
- **Nobody makes a header by hand.** The Filler policy gives no create right and no field to edit. The start is the cluster's own act: it makes the header as the platform, with the person who starts as its owner, and the cells row in the same transaction. The right to start is a new generic ability, **`sheets.fill`** (like `sheets.publish`: the catalogue is closed and a bundle cannot add to it). A member's right to update the header exists only so that the decision API can say they may have its cells changed; no field of it can be edited.

### 2. Pinned to the version, for ever, by the database

The start names a version number. The insert trigger of `sheet_fill` refuses a version that is **not in use at that moment** (acceptance criterion 1: two people starting while an approver publishes a newer version each end on the version that was in use for them, never on a draft or an approved one). The owner and the number of the version, the header and the organization can never change (criterion 6). The fill-in is read **together with its pinned version** (`GET /api/v1/sheet-fills/{object}/{id}` returns the grid of that version), so it shows against its own structure whatever happens to the template: replaced by a newer version, taken back from the people, or retired (criterion 13). This read is decided by the fill-in's own access (the header), not by access to the template: a filler whose template was unpublished still reads what they filled.

### 3. The cells: shape B, canonical, checked in a fixed order

ADR-0173 section 6 recommended B or C. **B** is built: `{"formatVersion":1,"rows":[{"id":"...","cells":{"<columnId>":"value"|true|false}}]}`. B keeps the stable identifiers readable and is 1.4 times the size of C (about 3 KB against 2 KB stored for a typical fill-in); the saving of C is not worth positions that are fragile to debug before the real example has arrived. The document carries its format number, so another shape later is a new reader and a migration of stored fill-ins, never a change in place.

The document is **sparse and canonical**: a cell with no value is not stored, the rows of the sheet that hold nothing are left out, the rows of the sheet come first in the sheet's order and then the rows the filler added in the order given, every object's keys are in order, and the hash is of that text. `FillValidator` checks the bytes that arrived in a fixed order, and **the first stage with a problem answers alone**: the size before anything is parsed, the nesting, JSON with a repeated key refused, the shape, the limits (rows, the length of a text), text (no markup, no control character), the rows (an identifier used once; a row of the sheet or one the filler added, and added only where the sheet allows it) and the cells (the column exists in the pinned version, **the cell is an input cell**, the value fits the type of its column: text, a number as the digits typed, a real date, one of the listed values, yes or no). A problem is a stable code, fixed words and a place made of positions and identifiers; **nothing a person typed is ever repeated** (the hostile cases of `FillValidatorTest`). What an input cell is comes from the pinned sheet alone (`FillStructure`): a body cell is an input cell unless the sheet fixes it or a merged area covers it; a row the filler added has no cell the sheet fixes.

Rows (criterion 5): a sheet whose filler adds the rows (dimension 1) has no rows of its own; every row is the filler's, with an identifier the browser made and the server checks. A sheet that names its rows (dimension 2) has those rows fixed and, if its rows mode is fixed-and-repeatable, the filler may add more after them. Rows added live in the fill-in; the template is never touched.

**Complete or not:** a draft may be saved half done. **Required values and at least one row (dimension 1) are enforced when the fill-in is sent**, against the version as it is then, and again for a correction after submit.

### 4. The status is the cell table's, and the header holds a copy

The status (`DRAFT`, `SUBMITTED`, `RETURNED`, `APPROVED`) is kept in `sheet_fill` with the moves the database allows (draft or returned to submitted; submitted to approved, returned or back to draft) and cells that change only while the fill-in is a draft or returned. The header carries a **copy** of the status (a platform-written, indexed field), written by the cluster in the same transaction as every move, so that lists and filters of the record store can use it. The truth is the cell table; a test compares them.

### 5. Review is the approval engine, through a hook

The cluster implements `ApprovalHooks` for `InspectionFill` (`FillApprovalHooks`). **On submit** it refuses a retired template, asks the sheets module to move the fill-in to review (which checks the required values and a row against the pinned version, with a place in words), then moves the header's copy. **When the request ends**: approved becomes approved; **rejected becomes returned** (the filler changes it and sends it again, as a new request; the history keeps both); recalled or cancelled becomes a draft again. The organization's administrator builds a process on Fill-in in the approval setup; without one, "Submit for approval" says so. Who decides is the process's (the tasks), not a policy. A person asked to review a fill-in who may not read the header reads that one fill-in and nothing else (the open-task read of ADR-0189), exactly as for a version of a template. The engine's lock (ADR-0148) protects the header; the cells are not a record, so **the cell save asks the status itself** and the database refuses a change of the cells of a submitted fill-in.

### 6. A submitted fill-in may be corrected (decision 11)

Only by a person who may change the header **and** holds `approvals.override-lock` (the Approver policy): the ability that already passes a pending approval's lock, so there is no second rule. The change is a **counted correction**: the database lets the cells of a submitted or approved fill-in change only inside a transaction that sets `platform.fill_correction` and raises the count by exactly one; it is written into the history of the request while the review is pending, and audited by size, counts and the fingerprint, never the content ("no tracking of the change beyond the normal audit record"). A correction cannot take a required value away.

### 7. Who sees what

By the rules of every record (ADR-0115) with the object private and no administrator able to change that: **the filler sees their own** (they are the owner), the people who hold *view all* on fill-ins see all of them (the Approver policy and the new **Reviewer** policy, which holds nothing else), and a person with an open review task reads that one fill-in. Other fillers do not see each other's. The platform has no way to say "the fill-ins of this template" in a record rule, so view-all is for **every** fill-in of the organization; the cluster adds no rule of its own. A returned fill-in goes back to its filler because they are its owner and its status is returned. The filler may finish and send a draft after the template is **unpublished** or has a **newer version** (the fill-in is pinned and complete in itself); after the template is **retired** it stays readable and is not sent. Known limits: the owner can hand their fill-in to another person (the record store's owner endpoint) or share it; the new owner then sees it. Nobody can delete one.

### 8. The list

`GET /api/v1/fill-ins` (filters `templateId`, `status`): a page of headers read through the record store (so the visibility above applies unchanged), **newest first, by the key of the last one seen and never by an offset, without the cells**; then one statement over the fill-in rows of exactly those headers and one over the versions of the templates on the page. ADR-0173 measured 5.1 ms at any depth for the key and 32 ms at 7,000 pages deep for the offset. `templateId` and `status` are indexed fields. A start has its own endpoints (`GET /templates/{id}/fill-in-options`, `POST /templates/{id}/fill-ins`).

### 9. Limits and settings

`platform.sheets.fills.max-bytes` (1,000,000, checked on the announced length and on the bytes read), `max-rows` (1,000), `max-depth` (6); the length of a text is the sheet's own `max-cell-chars`. The database's own ceilings: 5,000,000 bytes, 10,000 rows. Metrics `platform.sheets.fills{operation,result}`, `platform.sheets.fill.bytes`, `platform.inspection.fill{act,result}`; audit `sheets.fill.started|saved|corrected|submitted|reviewed` and `inspection.fill.started`, by identifiers, version numbers, sizes, counts and the hash.

### 10. What is not built (FF2 or later)

Attachments (the record store's file endpoints exist on the header but no screen uses them), reportable columns copied to a typed table and reports on them, partitions by month and the archive of old fill-ins to the object store, a per-cell patch, a number for each fill-in, a notice to the filler when a fill-in is returned beyond what the approval engine already sends, and choosing the real shape (B or C) from the real example (open item B).

## Consequences

- New: table `sheet_fill` (V069); module `sheets` gains `FillLifecycle`, `FillStatus`, `FillRefusal` and the endpoints `GET /api/v1/sheet-fills/{object}/{id}` and `PUT .../cells`; the ability `sheets.fill`; the object `InspectionFill`; the policy **Reviewer** and the changed Filler and Approver policies; module `inspection` gains the start, the options, the list and `FillApprovalHooks`; settings `platform.sheets.fills.*`.
- Changed: the architecture test names two places that take the platform's door to records (retiring a template and the header of a fill-in); `FillLifecycle` can be named by the cluster only.
- No new module edge. A template, a version and a fill-in are never deleted by anything this record adds.
- ADR-0173 section 6 is built as far as: shape B, the key-paged list without the cells, the pin. Not built: partitions, archiving, the typed projection (FF2).
