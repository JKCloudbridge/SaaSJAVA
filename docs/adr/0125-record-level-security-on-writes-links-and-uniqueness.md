# ADR-0125: Record-level security on writes, links and uniqueness

- **Status:** Accepted
- **Date:** 2026-10-14
- **Sprint:** S17A
- **Related:** [ADR-0091](0091-the-write-pipeline-and-its-order.md) (the seam), [ADR-0097](0097-links-between-records-on-write.md), [ADR-0106](0106-record-links-and-delete-behaviours.md), [ADR-0111](0111-uniqueness-of-field-values.md), [ADR-0112](0112-the-pair-of-parents-of-a-junction-is-unique.md), [ADR-0113](0113-recalculation-of-stored-formula-results.md), [ADR-0115](0115-the-record-access-model-and-how-it-reaches-a-statement.md), [ADR-0117](0117-explicit-sharing-and-who-may-share.md), [ADR-0118](0118-view-all-modify-all-and-one-evaluation.md)

## Context

Sprint 17 made the **read** side of record-level security complete: a list, a query, a single read, a search and the resolution of links all add the member's admission to their statement (ADR-0115). It left the **write** side loose, on purpose, because the question "may this member change this record?" needed the same evaluation to exist first:
a change of a record by identifier on a Private object was decided by the object permission alone, the recycle bin ignored records altogether, a link could point at any live record of the target object, and the wording of a duplicate refusal named "another record".

## Decision

1. **A change of an existing record is answered exactly as the single read of it** (the record permission stage, `RecordPermission`, ADR-0091's seam between the gate and the write pipeline). A record the member cannot read is `NOT_FOUND` with the words of the read. A record they can read and may not change is `FORBIDDEN`. The stage runs **before any value is judged**: an invalid body for a record the member cannot reach is `NOT_FOUND`, for a record they can only read it is `FORBIDDEN`, never `VALIDATION_ERROR`, so the order of the answers reveals nothing a read would not. It applies to update, delete, restore and removal for good; bulk and import run through the same code, record by record.
   - *Update* asks the `EDIT` admission, *delete, restore and purge* the `DELETE` admission. Both come from `RecordVisibility.constraintFor(object, member, access, action)`, the one place that already handles modify-all and view-all and turns the admission of `security` into a condition (ADR-0118). **There is no second rule**: the condition is run against the one record (`StorageStrategy.find(..., condition)`, `idsMeeting`), so the list, the read, the change and the removal cannot disagree for the same member and record; `RecordWriteSecurityIT` holds all four to the decision API over a matrix of sharing configurations.
   - A **create** needs no new stage: the owner is the caller, and the default, the hierarchy and the rules apply to the record from the next question as they do to every record. A caller always reaches a record they own.
   - Cost: with the default (Public Read/Write) the admission is `Everything`, no condition is added and nothing is queried beyond the old code; on a Private object a change costs two more reads of one record by identifier.
   - A change of owner raises the version of the record, which the optimistic check of the write catches; a share taken back in the same instant as a write is seen at the next question (ADR-0117).
2. **The recycle bin follows the same rules.** A record keeps its owner and its shares when it is binned, so the rules judge it as they judged it alive. The bin lists the records the member may bring back (the `DELETE` admission, which is contained in `READ`); restoring or removing for good a record they cannot read is `NOT_FOUND`, one they can read and not delete is `FORBIDDEN`. Until this sprint any member who could delete in the object saw every binned record of it.
3. **A master takes its details with it only if the member may remove them too** (extends ADR-0106's object-level rule to records): the cascade of a removal and of a restore checks the `DELETE` admission of every detail, one question per detail object, and refuses the whole call with `FORBIDDEN` and "You may not remove the records that belong to this one." without naming a detail (the member may not be able to see it). The other behaviours are integrity maintenance and run as the platform without a right over the other record: **clear** empties the pointer of records the member may not see, **refuse** answers that records refer to this one without naming any.
4. **A link can point only at a record the member can read.** The check of ADR-0097 point 1 now asks, per target object: may the member read the object at all, and is the record live and among the records they may read. A record that does not exist, one in the recycle bin, one of another object, one the member cannot read and any record of an object they may not use all give the same answer, "The linked record does not exist.", at the field. Before this sprint a member without any permission on the target object could still find out which identifiers exist there by writing links. Only a *change* is checked (ADR-0097 point 2): a link the write does not change is not judged again, so a record can still be saved after the member lost sight of its target.
   - Reading a record never shows more of a linked record than its identifier when the member cannot read the linked record: this was already true of the lookups of a query (ADR-0107, ADR-0115); `RecordLinkVisibilityIT` holds it to that.
   - Targets a platform module owns (`User` and the like) are unchanged: a yes-or-no from the reference directory (ADR-0099).
5. **Uniqueness runs across the whole organization and says only that the value is in use.** The check is the statement of ADR-0111 and the unique index of the database; neither is scoped by sharing, because a constraint that depended on who asks would not be one. The words changed from "Another record already has this value." to "**This value is already in use.** This field must be unique." (and "**This combination is already in use.**" for the two parents of a junction); a restore that would duplicate says that a value in a unique field is in use. What the refusal can reveal is only what any "taken" message reveals: **that** the value is in use in the organization. It never says which record, who owns it, whether the member could read it, or how many; the answer is byte-for-byte the same for a member who can see the record and one who cannot (`UniquenessAndVisibilityIT`). The count that refuses to make a field unique over duplicates (ADR-0111) is shown to the administrator who edits the setup and says how many, never which.
6. **Background work stays the platform's.** The clean-up of the recycle bin (`purgeDeletedOlderThan`), the recalculation of stored formula results (`QueryService.scan`, `StorageStrategy.updateCalculated`), the backfills of copies and links and the file clean-up never ask `RecordVisibility`: they process every record of their organization, are attributed to no member (their audit records have no actor), and change no owner, no share and no version. `BackgroundJobsAndRecordSecurityIT` runs both passes on a Private object whose records belong to people who cannot see each other and compares owners, versions, times and shares before and after.
7. **No audit of reads.** Sprint 17's documents call for no access audit of any record kind, and this sprint adds none: the existing audit of changes (by object, identifier, version and field names) is unchanged. A trail of who read and who was refused is added when a requirement names which records and why.

## Alternatives considered

- **Put the stage inside `WritePipeline.run`.** The pipeline judges the record *after* the change and begins with the shape of the body; a stage inside it would let `VALIDATION_ERROR` answer before the record was found, which reveals that a record exists. The stage is part of the record rules (`DefaultRecords`), where the record is read first, as ADR-0091 already said ("a record that does not exist ... is answered before any value is judged").
- **A Java rule for who may change a record.** Rejected for the reason of ADR-0115 point 2: one evaluator, the statement.
- **Link only to what exists, check readability on read.** Rejected: it lets a member learn which identifiers exist and write a pointer they cannot read back. Refusing at the write is cheap (one question per target object) and closes the oracle.
- **Cascade a removal regardless of the details' owners (as a master's controller).** Rejected: it lets a member remove records they could not remove directly, which ADR-0106 already forbade for the object permission.
- **Hide uniqueness conflicts with an invisible record.** Impossible without breaking the constraint: the alternative, accepting the duplicate for members who cannot see the other record, would make the data wrong. The honest minimum is the wording above.

## Consequences

- Closed: "do not run this branch with a Private object in production before 17A" (Sprint 17 manual steps).
- A member without read permission on a target object can no longer link to it; any test or script that did so needs read on the target (the shared test helper `person(...)` now grants it).
- The wording of three messages changed (a unique field, a junction pair, a restore); the smoke script and two tests were updated; clients that matched the words should match the code and the field instead.
- The API descriptions of the record endpoints say what the write side does; the OpenAPI document and the TypeScript client were regenerated.
- Still not built: a deny rule, an access audit trail, screens.
