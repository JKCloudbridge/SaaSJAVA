# ADR-0186: The sheets module: versions, the owner seam, the shape of a sheet and the size of a request

- **Status:** Accepted (the product owner answered "yes to all" on 2026-10-22 to the written plan and its five questions; the technical choices were delegated)
- **Date:** 2026-10-22
- **Sprint:** FA3 (Functional track)
- **Related:** [ADR-0172](0172-the-grid-component-and-the-adapter.md) and [ADR-0173](0173-the-canonical-grid-json-and-its-limits.md) (both Accepted by this sprint), [ADR-0174](0174-template-versions-and-approval-together.md) (the lifecycle; the parts built here are named in section 8), [ADR-0070](0070-definitions-are-json-checked-by-a-schema.md), [ADR-0083](0083-storage-benchmark-result-gate-g1.md), [ADR-0115](0115-the-record-access-model-and-how-it-reaches-a-statement.md), [ADR-0129](0129-record-screens-the-members-description-names-and-validation.md), [ADR-0148](0148-record-locking-while-an-approval-is-pending.md), [ADR-0180](0180-names-the-module-the-objects-and-the-words.md), [ADR-0181](0181-the-solution-framework.md)
- **Evidence:** `SheetVersionGuardIT` (46 direct statements as the application role and as the owner), `SheetVersionsIT`, `SheetVersionsAccessIT`, `SheetRacesIT` (two real instances), `SheetLimitsIT`, `SheetListCostIT`, `SheetHostileCorpusTest` (110 constructs), `SheetGridPropertyTest`, and the web tests of the model and the grid

## Context

FA0 decided what a sheet is (a grid of five column types, header rows, merges, three styles and a size, stored sparsely, up to 1 MB), that it is kept as numbered versions in a table of its own, and that the grid is our own component. FA3 builds the generic part: the module `sheets`, the table, the endpoints and the editor. Building it raised decisions that the earlier ADRs left open or stated in two ways. This one records them.

## Decision

### 1. One generic module, one table, and the owner is a parameter

The module `sheets` knows no business word. A sheet belongs to **one record of one object** (`owner_object`, `owner_id`); the table is `sheet_version` (V064). **Which objects may own a sheet is declared by a shipped solution** (`sheetOwners` in `solution.yml`, read by the `solution` module and handed to `sheets` through the shared-kernel contract `SheetOwnerDeclarations`, an optional bean: the same inversion as the number series). Without it any member who may change a record of any object could attach megabytes to it; with it only the declared objects can, and an organization without the plan feature does not have the object at all, so it has no sheet either. `SolutionBoundaryTest` is unchanged: the cluster's words stay in the bundle, the page and the tests.

### 2. The seam that says who may read or change a sheet

Generic endpoints keyed by the owner: `/api/v1/sheets/{ownerObject}/{ownerId}/versions` (list, start a draft), `.../versions/{versionNo}` (one version with its grid) and `.../versions/{versionNo}/grid?version=n` (save a draft). `SheetOwners` is the **only** place that decides, in this order: the member behind the request (the host and the token, never the request); the object may own a sheet; **the record exists and is one the member reads** (`RecordTitles`, which passes the stages a list passes: object, field and record-level security); the decision API says read; and for a change that it says update (read but not update is "forbidden"). Every other case is "not found" with the same words, so nothing is learned about what exists. A sheet has no permission of its own and there is no second Java rule for who may see a record ([ADR-0115](0115-the-record-access-model-and-how-it-reaches-a-statement.md)): a share of the record to a person, a group or a role reaches its sheet through the same answer.

**A defect found by the tests, and why `RecordTitles` is asked.** The decision API alone answers "yes" to any identifier for a member who may view every record of the object, including an identifier that names no record; the first version of this seam therefore listed an empty sheet for a made-up record and would have let a sheet be attached to nothing. The existence check closes it. It costs an edge `sheets -> data` (for `RecordTitles` only; `data` does not depend on `sheets`).

**What a member who may only read sees.** The versions that are in use or were (`ACTIVE`, `SUPERSEDED`, `RETIRED`); a draft, a version in review, an approved-but-not-published, a rejected or a withdrawn version answers "not found" ([ADR-0174](0174-template-versions-and-approval-together.md) section 3), so a share can never leak a draft. A member who may change the record sees every version. Older versions are never removed and stay readable as above, which is what lets the fill-ins of the following set pin the exact version they were filled in.

**Known limit, for FA4.** "May change the sheet" is "may update the record". The Approver policy of FA4 holds the update right (for the override), so an approver could also start a draft. If the business wants authors and approvers apart, FA4 narrows it in `SheetOwners` and nowhere else; the lock of the record by a pending approval and the review edit of [ADR-0174](0174-template-versions-and-approval-together.md) section 4 are also asked there.

### 3. Where the shape of a sheet is stored (it differs from ADR-0174 section 1)

[ADR-0174](0174-template-versions-and-approval-together.md) section 1 puts the dimension and the rows mode on the header record **and** the format of [ADR-0173](0173-the-canonical-grid-json-and-its-limits.md) puts them in the grid: two truths. **They are stored once, in the sheet.** The first version names them; every later version keeps them. The module refuses a different shape (VALIDATION_ERROR on a copy; at the database an insert that differs from the first version, and an update of a version after the first, is refused by a trigger). The shape may change only while the first version is the only one and is still a draft, because a mistake there would otherwise be permanent and nothing is ever deleted. `dimension`, `rows_mode` and `grid_bytes` are also columns of the version row, copies of facts of the grid, so that a list needs not read it. The header record gets **no** new field in FA3, and the reviewer and approver fields are added in FA4 (they live in the record's JSON: no migration).

### 4. The table and its protections (V064)

Tenant-scoped, forced row level security, the base columns and guards, **no index on the JSON** ([ADR-0083](0083-storage-benchmark-result-gate-g1.md)). Unique: `(tenant, owner_object, owner_id, version_no)`, and one `DRAFT`, one `IN_REVIEW` and one `ACTIVE` per sheet (partial indexes), which is why two requests for "a new version" end with one draft whatever the application does. A trigger refuses, to the application role and to the owner alike: a delete and a soft delete; a start that is not `DRAFT`; a status move that is not part of the lifecycle of [ADR-0174](0174-template-versions-and-approval-together.md) section 2 (strictly that table: `DRAFT→IN_REVIEW`, `IN_REVIEW→APPROVED|REJECTED|WITHDRAWN`, `APPROVED→ACTIVE`, `ACTIVE→APPROVED|SUPERSEDED|RETIRED`; a move the table lacks is a new migration that replaces the function); a change of the owner or the number; a change of the grid, its hash or its size once the version is not a draft, **except** the counted edit of an approver while `IN_REVIEW`, which needs the session setting `platform.review_edit = on` and a rise of `review_edits` by exactly one (the pattern of `platform.record_recalculation`); the setting is set by no code in FA3 (the endpoint that sets it is FA4's). The numbers of a version are never reused because rows are never removed; `max-versions-per-owner` (1,000) bounds a sheet.

### 5. The grid is checked in a fixed order, and what it stores is canonical

`SheetGridValidator` runs the stages in this order and **the first stage with a problem answers alone**: the size of the bytes that arrived (before anything is parsed), the nesting of the raw text, JSON with a **repeated key refused** (strict duplicate detection: a browser's parser would keep the last and hide the first), the shape against the schema file `sheet-grid.json` (copied into the OpenAPI document), the limits that are settings, text (no markup, no control character, no text-reordering mark), identifiers unique across columns, header rows and rows, picklist lists, the rows mode of the dimension, cells (they point at a real row and column, header cells are fixed, a value fits its column, **a style only on a fixed cell: bold, italic and the four named sizes are refused on an input cell, an empty body cell included**), merges (one zone, written top left to bottom right, more than one cell, never overlapping, nothing under a merged area but its top left cell). Where the spike's checker was looser than the ADR (a repeatable sheet that names rows, a two-dimensional sheet that is repeatable only) the ADR wins. A problem has a stable code, fixed words and a place made of names of the schema, positions and the keys of the map of cells; **a property the schema does not define is shown as an ellipsis even when it looks like a word**, found by the corpus test. Nothing a person typed is ever repeated.

**Canonical form and hash.** An accepted grid is normalised (an empty text is nothing, a style that changes nothing is dropped, the kind of a cell is stated only where the rules do not imply it, a cell that holds nothing is not stored, merges are sorted) and written with every object's keys in order and compact; its SHA-256 over those UTF-8 bytes is the hash. The same grid always has the same hash whatever order its keys arrived in, and **whatever the database does to the order of keys of its JSON type**, which is why the hash is computed in the application over the text and not read back. The browser writes its documents in the same form, so "has this changed?" is a comparison of two texts.

### 6. The size of a request

The grid is the **whole body** of the save (a raw JSON body, the schema `SheetGrid` in the OpenAPI document, the row version in the address): that makes "before it is parsed" literal. `SheetBodyLimit` refuses an announced length above `max-bytes` (1,000,000) with `PAYLOAD_TOO_LARGE` before the body is read; the controller then **counts the bytes it reads and stops at the limit**, so a body with no announced length (chunked) is bounded too, by the application and not only by the proxy (the deployment text still asks the proxy for a limit). Every other request of the module is held to `small-body-bytes` (4,096). The database's own ceiling for a grid is 5,000,000 bytes, whatever the setting. The limits are `platform.sheets.limits.*`; the API states them in the answer of the list so that the screen holds no number.

### 7. The browser

`platform-web/src/lib/sheets/` holds the pure model (the operations as functions from a document to a document or to the reason in plain words, history that keeps documents, the adapter, the hints, the words of a status); `src/components/sheets/` holds the grid, the form view, the grid view, the version list and the workspace; the one dependency is the virtual-scrolling helper of ADR-0172 (MIT, version 3.14.21, the one the prototype measured), exact in `package.json` with the lock file. The grid is read-only below 40 rem and says so; the form view is the way to build on a phone. A text edit is committed when the person leaves the box (one step of the history, not one per key). The grid never decides a permission: the buttons follow `canChange` and the status the API gave, and every request is decided again.

### 8. What FA3 leaves, and how FA4 drives it

> **Answered in FA4 ([ADR-0188](0188-the-template-lifecycle-the-cluster-module-publishing-and-the-master-list.md), [ADR-0189](0189-who-sees-a-template-the-fixed-private-default-abilities-and-field-rights-of-shipped-policies-the-approvers-edit-and-the-open-task-read.md)):** the moves are `SheetLifecycle` in `sheets`; `SheetOwners` asks the lock's ability for the correction in review and the open task for the read of a version in review; the draft beside a version in review stays as section 3 here says.

No endpoint moves a version out of `DRAFT`: no submit, approve, publish, retire, no hook, no step flag, no number. The database already enforces the whole lifecycle, and `SheetVersionGuardIT` drives every move by direct statements; FA4 adds the service methods that make the moves (in `sheets`, with `SheetOwners` asking the lock and the review edit) and tests them through the same table. [ADR-0174](0174-template-versions-and-approval-together.md) contradicts itself on one point: section 2 row 2 says saving a draft is refused while the header is locked, section 3 says the author keeps working on the next draft while another version is in review. **Section 3 is followed**: a draft is in the version table, not in the header, so the header lock does not stop its save; the lock and the review edit concern the `IN_REVIEW` row and arrive with FA4.

## Consequences

- ADR-0172 and ADR-0173 are **Accepted** (built as written, with the font size and the rule on styles above); the parts of ADR-0174 built here are the version table, its statuses and indexes, the immutability trigger, the delete refusal, the automatic numbers and the read rule by status.
- A new module `sheets` (edges `tenant`, `security`, `data`), one shared-kernel contract (`SheetOwnerDeclarations`), one migration (V064), four endpoints, and one new optional key in the solution file (`sheetOwners`).
- The hash is of the canonical text, not of the stored `jsonb`; a future format version is a new reader plus a migration of stored versions.
- **Measured** (`SheetListCostIT`, a sheet of 200 versions of about 100 KB each, 21 MB with its out-of-line storage and indexes, local PostgreSQL 18): the list of its versions touched **10 pages in 0.47 ms**; one grid (the newest) **48 pages in 0.6 ms**; reading every grid **3,165 pages in 92 ms**. The list never selects the grid; one statement does, and a test fails if a second appears.
- Not decided here: reports across versions; whether a column may take its list from a platform picklist (ADR-0173); a task-scoped review edit (ADR-0174 section 4).
