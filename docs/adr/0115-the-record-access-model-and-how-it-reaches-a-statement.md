# ADR-0115: The record access model and how it reaches a statement

- **Status:** Accepted
- **Date:** 2026-10-13
- **Sprint:** S17
- **Related:** [ADR-0040](0040-effective-permissions-and-the-read-contract.md) (union only), [ADR-0047](0047-public-groups.md), [ADR-0050](0050-the-permission-decision-api.md) (the record is accepted and ignored), [ADR-0053](0053-the-security-cache-and-its-version.md), [ADR-0100](0100-the-query-model-and-its-stages.md) (the seam `RecordVisibility`), [ADR-0105](0105-filters-and-orders-without-an-index-on-large-objects.md), [ADR-0116](0116-defaults-hierarchy-and-sharing-rules.md), [ADR-0117](0117-explicit-sharing-and-who-may-share.md), [ADR-0118](0118-view-all-modify-all-and-one-evaluation.md), [ADR-0119](0119-record-predicates-in-the-plan-and-the-owner-index.md)

## Context

Until Sprint 16 a member who may read an object reads every record of it. Sprint 17 makes "which records?" depend on the owner of the record, the role hierarchy, public groups, sharing rules, explicit shares and two object flags (view-all, modify-all). The data is spread over two modules: the role tree, the groups and the rules are the `security` module's tables; the records and their shares are the
`data` module's. The module rules forbid `data` to read `security` tables ("never read or write another module's tables"), and `security` cannot depend on `data` (data depends on security). The same answer must come out of a list, a query, a single read, a lookup and `Decisions.can(..., RecordRef)`, by construction and not by copies of a rule.

## Decision

1. **`security` publishes a closed description, `data` evaluates it.** A new root-package contract `RecordSecurity` answers, for a member and an object, a `RecordAccess`: three `Admission`s, one per `RecordAction` (`READ`, `EDIT`, `DELETE`). An `Admission` is a small sealed tree of conditions a record must meet: `Everything`, `Nothing`, `AnyOf(...)`, `OwnedBy(users)`,
   `SharedWith(grantees, atLeast)` and `Meets(rule, criterion)`. `security` resolves everything it owns (the role tree, groups with their nesting, rules, the defaults, the object flags) into those leaves; `data` turns the tree into plan nodes (ADR-0119) and into one statement. Nothing in `data` reads a `security` table, and `security` reads no record.
2. **One evaluator: the statement.** The list, the query, the single read (`find ... and <admission>`) and the lookup resolution add the admission as a condition of the statement they already run. `Decisions.can(member, object, action, RecordRef)` asks `RecordMatcher`, an interface of the security root that `data` implements (the same inversion as `ObjectCatalog`, implemented by `metadata`), to evaluate the member's
   admission against the one stored record **with the same statement builder**. There is no second Java implementation of the rules that could drift. For tests, a pure reference interpreter of the tree over explicit facts (test code only) is the oracle that the statement is held to by a table-driven and a property test (ADR-0118).
3. **The description is bounded; the bound is measured.** The only unbounded leaf is `OwnedBy(users)`: a manager's subordinates, the owners behind a sharing rule. Measured on PostgreSQL 18 with 1.3 million records, forced row level security, an index on the owner (tenant, object, owner, id) and a `uuid[]` parameter: 1 owner 2.3 ms; 50 owners 10.5 ms (the whole selective set found by the id
   order); 500 and 5,000 owners about 1 ms; 20,000 owners 1.1 ms, with planning 0.3 ms (50 owners), 4.5 ms (5,000) and 16 ms (20,000): planning grows with the array, execution does not. The bound is therefore `platform.security.records.max-owners` = **20,000 distinct owners** in one member's description of one object. The sets are carried as one text parameter converted in the statement
   (`cast(string_to_array(:owners, ',') as uuid[])`), not as a list of placeholders (a placeholder per value would stop at 32,767 and give every size its own plan).
   **When a description would exceed the bound it fails closed:** the owners beyond the bound are dropped from the description in a fixed order (the member's own id first, then the rest by identifier), the description is marked `truncated`, the member's lists show what the rest of the description admits, and the event is reported once per security version to the error tracking and in the metric
   `platform.security.records.truncated`. A wrong *grant* is never produced; an organization that reaches the bound uses a group-based sharing rule (a group is one leaf and the members of a group are not enumerated in the statement) or splits the hierarchy. The path beyond the bound (a semi-join through a function that `security` publishes) is
   written down here as the next step and not built: no organization of this platform is near the bound, and building it before it is needed would be a second evaluator.
4. **Why not the alternatives.** *A stamp of the owner's role path on every record* (backfilled): a role move or a change of an owner's role would have to rewrite every record the person owns before the next question, or the answer would be stale for a while, and the bound "the next question after the commit" (ADR-0053) would be lost; an asynchronous recalculation of the stamps is exactly the gap this
   platform refuses. *Materialised share rows per record and per user*: write amplification on every record insert and every role change, for the benefit of a read path that the measurement shows needs none. *A join from the data statement against `security` tables or a view*: breaks the module rule and makes the two modules one. *A temporary table of visible owners per request*:
   catalogue churn on every request and no statistics for the planner.
5. **Cached behind the security version (ADR-0053).** The `RecordAccess` of a member for an object is a new kind of answer in `SecurityCache`, kept with the version it was computed under, never used or filled by a transaction that wrote. Every table that feeds it carries the version trigger (V044): `object_sharing_setting`, `sharing_rule`, and the tables that already did (`security_role`... `member_access`, `public_group*`, `object_permission`, `membership`).
   **Explicit shares (`record_share`) do not raise the version and are not cached:** the description holds only *who* the member is for sharing (their user identifier and their groups), and the statement reads the live share rows. A share is therefore visible at the next question without any invalidation, and sharing a record does not drop the caches of the whole organization.
6. **The owner is a user; the hierarchy is made of memberships.** `object_record.owner_id` is a user identifier. `member_access` gains `user_id` (V044), copied from the membership by a trigger and immutable, so that `security` can turn "the members below me" into owners without reading the membership table.
7. **What stays out.** The record-permission stage of the write pipeline, links that respect visibility and the uniqueness answer that does not reveal (Sprint 17A) are not built here. This ADR leaves the seam they need: `Decisions.can(member, object, EDIT|DELETE, RecordRef)` answers for one record with the evaluation above. The writes of this sprint (bulk, import, owner change) go through the
   same gate and pipeline as a single write, so 17A's stage applies to them without a change here.

## Consequences

- With the default Public Read/Write (ADR-0116) the description is `Everything` for every member: no extra condition, no extra read beyond the cached description, and nothing changes for any existing organization.
- A member of a Private object pays one condition in the statement; the measured cost is in ADR-0119 and the benchmark.
- A move of a role, a change of a group, of a rule or of a default is visible at the next question on every instance (the version), while a share is visible at once.
- The bound on owners is a documented limit with a safe failure and a named way out.
