# ADR-0193: Fill-ins, the rest: attachments, reportable columns, the report and the archive

- **Status:** Accepted (the product owner delegated every decision on 2026-10-23: "do as you think better for production grade"; the recommendation of each question was built)
- **Date:** 2026-10-23
- **Sprint:** FF2 (Functional track, the following set, second half)
- **Related:** [ADR-0173](0173-the-canonical-grid-json-and-its-limits.md) section 6 (the volume), [ADR-0083](0083-storage-benchmark-result-gate-g1.md) and [ADR-0101](0101-the-index-policy-and-the-slots.md) (never an index on the JSON), [ADR-0120](0120-files-attached-to-records.md) (files), [ADR-0192](0192-fill-ins-the-header-record-the-cell-table-and-review-by-the-approval-engine.md) (fill-ins), [ADR-0115](0115-the-record-access-model-and-how-it-reaches-a-statement.md) (who sees a record)
- **Evidence:** `FillValuesTest`, `FillValueStoreSqlTest`, `FillFileRulesTest`, `OnlyTheValueStoreNamesTheTableTest`, `InspectionArchitectureTest`, `SheetHostileCorpusTest` (no database); `FillReportIT`, `FillArchiveIT` (real PostgreSQL and object store); web tests `report.test.ts`, `FillInReportPage.test.tsx`, `FillInsPage.test.tsx`. **Written, not yet run** when this was written (the testing session runs them).

## Decision

### 1. Attachments: the whole fill-in, with the rule of the lifecycle
Files go against the **whole fill-in** (its header record, through the record files of ADR-0120), not a row: a row can be removed or renumbered by the filler, a file would lose its place, and nothing in the requirements asks for a file on a cell. A file inherits the visibility of the header. What is new is a seam, `RecordFileRules` (shared kernel, found by object like the approval hooks), called by the file service after its own checks; the cluster implements it for `InspectionFill` (`FillFileRules`). A draft or returned fill-in takes and gives up files only for the person who started it; a sent or approved one only for a person who holds the ability to override the lock of an approval (the same "may correct" as the cells), which is **audited** (`inspection.fill.file.corrected`: fill-in, act, status, person; never a file name) and counted; an archived fill-in takes none. The rule can only refuse.

### 2. Reportable columns: one narrow typed row for each non-empty value
A column of a version can carry the optional flag `reportable` (`formatVersion` stays 1: the part is optional, absent means false, so no stored version changes and no hash changes). At most 20 per version (`too_many_reportable`; each costs rows). Every save of cells (the filler's and the counted correction) replaces, **in the same transaction**, the copy of that fill-in in `sheet_fill_value` (V070): one row for each non-empty reportable cell, the value in a typed column (text for text and list, numeric, date, boolean), with the sheet and version repeated so a report is answered from this table alone. A version with no flagged column does nothing extra. A refused save leaves the old copy (same transaction). The table has one partial B-tree index for each kind on (sheet, version, column, value, fill-in); never an index on the JSON.

*Narrow rows against typed slots on the fill row:* slots (the pattern of ADR-0101) would give one row per fill-in row instead of one per value, but need a mapping of columns to slots for each version, up to 16 indexes on the big table and a rewrite of the fill row on every save. Narrow rows are exact, simple to test differentially and cost a row per non-empty flagged cell; the cap of 20 and "non-empty only" bound it. Known cost: a template-year of 365,000 fill-ins of 50 rows with 5 flagged columns is about 90 million rows; if the measurement on the intended instance says that is too heavy, slots are the next step and nothing outside `FillValueStore` changes.

### 3. The report: one condition, no export
The smallest useful thing: **one condition on one reportable column** of one version of one template: equals, one of (up to 100), or a range (number or date; either bound may be left out). The answer is a page of fill-ins in the form of the list, newest first, paged by the key of the last one looked at, never by an offset, without the cells. Several conditions, counts and an export (a CSV file name would carry text of the organization) are left for later.

**Visibility is not decided by the report.** The sheets module (`FillReports`) says which fill-ins hold a value; the cluster asks the record store's own query which of those headers the caller may see (`id in (...)` plus the status filter), in batches of 50, so a person sees exactly the fill-ins of the list by the same code (ADR-0115). A caller who sees few of many matches makes the search look through more batches (at most 20 for a page); the page can then be short and still carry a cursor: only a missing cursor means the end. To choose a column the caller must see the template. The value travels in a POST body, never an address, and is never logged, audited or tagged.

### 4. The archive: one compressed document in the object store, the row stays
An approved fill-in whose review ended more than `platform.sheets.archive.age` ago (default 365 days, never less than 30) has its cells moved by `FillArchiveJob` to the object store as **one gzip document** (key `fill-archives/<organization>/<fill-in>`). The row stays (status, pin, size, row count, **hash of the canonical cells**, a pointer `archived_at`, `archive_key`, `archive_bytes`; V071) and the cells column holds `{}`. The report values (V070) stay, so an archived fill-in is still found. Nothing is deleted. Reading: the sheet fill-in endpoint unpacks (bounded), checks the hash against the row's and refuses to show a document that does not match (503, counted). An archived fill-in is read-only for everyone, including the counted correction.

*Crash safety and two instances:* each fill-in is its own transaction in its organization's own tenant context (no system scope, like the recycle bin): take the advisory lock every save takes; re-read; re-write the cells canonically and **stop unless the hash is the row's**; store; **read back and verify before the row lets go**; then one update that the database allows only inside the archive window (`platform.fill_archive`, V071) and only for an approved, unarchived fill-in. A crash before the update leaves at most an unreferenced document the next pass overwrites with the same bytes; after it the move is done. A second instance waits on the lock and finds the work done; the database refuses a second move. A pass moves at most `batch-size` (50) fill-ins for each organization.

### 5. Volume: partitions are not built; compression stays as it is
Targets (set before building, not moved after a number): save of a 50-row, 20-column fill-in with 5 reportable columns p50 under 50 ms and p95 under 150 ms; a list page at any depth under 30 ms; a report page on 365,000 fill-ins under 200 ms; archived cells read back under 300 ms. **These have not been measured yet**: the run on the intended instance is the testing session's (condition 6 of ADR-0083). Monthly partitions are **not built**: (a) the invariant "one fill row for each header record" is a unique index on (organization, object, header) that PostgreSQL cannot keep across partitions unless the partition key (`created_at`) is part of it, which would weaken the uniqueness the guard and the pin rely on; (b) the archive removes the weight (the cells in TOAST are about 90 percent of a fill-in), so the live table after a year holds the rows of one year plus small stubs, about 2 GB for a template-year, below the "few hundred GB" threshold of ADR-0173 section 6; (c) compression in the database stays `pglz` (ADR-0173 measured it 11 to 31 percent smaller than `lz4`); the archive is gzip. Reconsider when the measurement on the intended instance, or the table size, says so; the archive unit is already one fill-in, not a partition, so partitions can be added later without changing it.

### 6. The real shape: B is kept
No real filled example exists in `Functional/Audit maintenance/`, so shape B stays. When one arrives, re-measure on it: stored size and save time of B against C for the real number of rows and filled columns, text that compresses worse than the generated vocabulary, and how many cells are empty. A change of shape is a new reader plus a migration of stored fill-ins by the format number, never in place.

### 7. Not built, with the reason
A notice to the filler when a fill-in is returned (the approval engine's own notices already tell them; a new notice kind touches the kind lists, the templates and the words in four places); a running number for each fill-in; a count of fill-ins per template on the template page (the record engine gives no total, and a count over all fill-ins would tell a filler how many others exist, which the private default forbids; a per-viewer count needs a query for each viewer).

## Consequences

- New: V070 (`sheet_fill_value`), V071 (archive pointer, replaced guard function, index); `FillReports` (sheets), `RecordFileRules` and `RecordFileRefusal` (shared kernel); `FillReport` and `FillFileRules` (inspection); the endpoints `GET /api/v1/fill-ins/report/columns` and `POST /api/v1/fill-ins/report`; `archivedAt` on the fill-in summary, the list rows and `FillLifecycle.Summary` (plus `startedBy`); settings `platform.sheets.archive.*`; the page key `fill-in-report` and the "Report" entry of the application.
- ADR-0173 section 6: built as far as the typed projection (item 4) and the archive (item 3); partitions (item 2) deliberately not; the shape (item 1) kept as B.
- No change to a template or a version; no module edge was added (`inspection` already depends on `sheets`; `data` gets the file-rule seam from the shared kernel).
